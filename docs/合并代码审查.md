### N-S2｜DesktopMcpServer.kt:39-60, 134-148；Main.kt:161-180｜本地 MCP 服务无鉴权、不校验 Origin/Host，网页可以改工程
- **问题**：服务只绑了 `127.0.0.1`，这一点是对的。但它：①没有任何令牌；②不检查 `Origin`、`Host`、`Content-Type`；③桌面端启动时**无条件开启**，没有开关；④`studio_apply_patch` 可以写入任意积木（见 N-S3）。

  - **DNS rebinding**：攻击域名重绑到 127.0.0.1 后算同源，可以读到 `studio_get_project` 和 `studio_generate_code` 的响应，并任意写入。
  - 被注入的代码只进了撤销快照（标签「外部 MCP 补丁」），界面上没有醒目提示。用户之后点「真机运行」（StudioState.kt:485-493 不做任何扫描），代码就会在手机 AutoJs6 上执行，那里有完整的 Java 访问权限。
- **修复**：
  1. 启动时生成 32 字节随机令牌，要求 `Authorization: Bearer <token>`。界面里「复制地址」一并复制令牌和配置片段，令牌不落盘。
  2. 校验 `Host` 必须是 `127.0.0.1:<port>` 或 `localhost:<port>`。请求带 `Origin` 头时直接 403（IDE 客户端不会带）。要求 `Content-Type: application/json`。
  3. 默认关闭，在 AI 面板加开关；或者只开放只读工具，`apply_patch` 需要在 UI 里逐次确认。
  4. 工程被外部补丁改过之后，置「含外部修改」标记；真机运行前先弹 diff 确认。

### N-S3｜BlockPatch.kt:53, 55-79, 123-145｜BlockPatch 的「受控通道」挡不住代码注入
- **问题**：
  1. `rawJs` 被明确放行（:135 `if (op.block.type != "rawJs")`），补丁里直接加一个 `rawJs` 就能执行任意代码。
  2. `CODE_INJECTION_RE` 只匹配 `function(`、`=>`、`require(`、`eval(` 四种写法，很容易绕开。比如 `java.lang.Runtime.getRuntime().exec("…")`、`engines.execScript(…)`、`shell("…")`、`files.remove(…)`、`http.get(…)`，都匹配不上。
  3. 很多参数是原样拼进代码的：`varSet/varAssign.name`（Catalog.kt:117-127 直接输出 `let $name = $e`，而 `name` 是 TEXT 类型）、所有 `expr` 和 `cond`（EXPR 类型）、选择器的 `expr`（BlockDef `selector()` 输出 `($expr)`）。旧约束「标识符校验 Diagnose.isJsIdentifier」只在诊断时提示，生成代码时不强制，补丁通道也不调用 Diagnose。
  4. AddBlock 只校验顶层块：:61 只检查 `op.block.type`，:136 只遍历顶层 `params`。嵌套在 `children` 里的块，类型和参数都不检查。
  5. UpdateParam 不检查 key 是否属于该积木的定义、值类型是否匹配、SELECT 的值是否在选项里。
- **触发场景**：外部 AI 或网页（经 N-S2）发送 `AddBlock{block:{type:"varSet",params:{name:"x=java.lang.Runtime.getRuntime().exec('…');var y",expr:"1"}}}`，或者发送 `AddBlock{type:"if", children:{body:[{type:"rawJs",…}]}}`。护栏都会放行，生成的脚本在真机上执行。还可以在 `kitBoot` 之前插一个 `rawJs`，写 `Kit.configure({...})` 或者覆盖 `Kit.boot`，把护栏整个关掉。
- **修复**：改成白名单式校验，递归检查每一个块：
```kotlin
private fun validateBlock(b: Block, errs: MutableList<String>) {
    val def = Catalog.byType(b.type) ?: return errs.plusAssign("未知积木类型 ${b.type}")
    if (b.type == "rawJs") errs += "补丁通道禁止 rawJs"
    b.params.forEach { (k, v) ->
        val pd = def.params.firstOrNull { it.key == k } ?: return@forEach errs.plusAssign("${b.type} 无参数 $k")
        when (pd.kind) {
            ParamKind.CODE, ParamKind.EXPR -> if (v.asText().isNotBlank()) errs += "补丁通道禁止写入表达式/代码参数 ${b.type}.$k"
            ParamKind.SELECT -> if (pd.options.none { it.value == v.asText() }) errs += "${b.type}.$k 取值非法"
            ParamKind.NUMBER -> if (v !is ParamValue.Num) errs += "${b.type}.$k 需要数字"
            else -> Unit
        }
        if (k in IDENT_KEYS && !Diagnose.isJsIdentifier(v.asText())) errs += "${b.type}.$k 不是合法标识符"
    }
    b.children.forEach { (slot, kids) ->
        if (def.slots.none { it.key == slot }) errs += "${b.type} 无插槽 $slot"
        kids.forEach { validateBlock(it, errs) }
    }
}
```
  更稳妥的做法是：AI 和 MCP 补丁只允许 `kit*`、`comment`、`log`、`toast`、`sleep` 等纯数据积木。同时建议在 CodeGen 层对 `varSet.name` 这类参数强制做标识符校验，不合法就生成注释，不要只靠 Diagnose。

## 二、中等

### N-M1｜UrlSecurity.kt:63-84, 39-61｜SSRF 校验可以绕过
- **问题与触发场景**：
  - **userinfo 绕过**：`http://x@169.254.169.254/latest/meta-data` 解析出的 host 是 `x@169.254.169.254`（:72 `substringBefore(":")` 没去掉 `@` 之前的部分），校验通过，实际连接的是 169.254.169.254。`http://a:b@169.254.169.254/` 解析出的 host 是 `a`，同样通过。
  - **数字形式 IPv4**：`http://2852039166/`、`http://0xA9FEA9FE/`、`http://169.254.43518/` 不匹配 `IPV4_RE`。JVM 的 `InetAddress` 接受十进制整数形式（CIO 引擎走这条路）；Android/OkHttp 的行为待确认。
  - **DNS**：没有解析后再校验，`169.254.169.254.nip.io` 或攻击者自己的域名都能指向元数据或内网地址。末尾带点的 `metadata.google.internal.` 也能绕过。
  - **IPv6**：AWS 的 IMDS IPv6 地址 `fd00:ec2::254` 没有算作元数据。`0:0:0:0:0:ffff:a9fe:a9fe`、`::169.254.169.254`、`[0:0:0:0:0:0:0:1]` 都识别不出来。
  - **阿里云元数据** `100.100.100.200` 只在 `allowLocal=false` 时才被拦，而所有调用方都传 `allowLocal=true`（StudioState.kt:779；LlmConfig.kt:50 的默认值）。
  - 误判：`:51` 用 `startsWith("fc")/("fd")` 判断，把 `fdroid.org`、`fcbarcelona.com` 这类域名也当成内网。
  - 重定向：Ktor 默认只对 GET/HEAD 跟随重定向，LLM 调用都是 POST，风险较低（待确认使用的 Ktor 版本行为）。
- **修复**：用 `io.ktor.http.Url(raw)` 或 `java.net.URI` 解析出真正的 host，有 userInfo 就直接拒绝。用 `InetAddress.getAllByName(host)` 解析出全部地址，逐个用 `isLoopbackAddress / isLinkLocalAddress / isSiteLocalAddress / isAnyLocalAddress` 判断，再加 169.254/16、100.64/10、fd00:ec2::254 黑名单。客户端安装 `HttpRedirect { checkHttpMethod = true }`，或者直接关闭重定向。

### N-M3｜Catalog.kt:692, 706；Aj6KitRuntime.kt:349-363, 693-714｜风控或超时后流程不会停
- **问题**：`$kit.click()` 在 guard 失败时返回 `{ok:false, reason:'guard'}`，`waitFor()` 在 guardRisk 失败时返回 null，但生成的代码都不检查返回值，流程继续往下走。只有专门放置的 `kitGuard` 积木会 `exit()`。运行时的设计原则是「④遇安全验证停下等人，绝不硬闯」，这里没做到。
- **触发场景**：出现「安全验证」后等了 90 秒仍未通过，下一个 `kitClick` 会再次进入 guardRisk：3 秒内的重复调用直接返回 false，超过 3 秒就再等 90 秒，如此往复。超过 `maxRuntime` 之后，每个动作只记一行「已达单次运行上限」，然后继续执行。
- **修复**：kitClick 生成成
  `var _r = $kit.click({...}); if (!_r.ok) { if (_r.reason === 'guard' || _r.reason === 'abort') { $kit.finish('failed'); exit(); } $kit.reportLeftover(<value>); }`。
  kitWaitFor 未命中时，同样按 `$kit.overBudget() || $kit.atRisk()` 判断是否退出。

### N-M5｜Catalog.kt:716-720 ↔ Aj6KitRuntime.kt:1793-1811, 1886-1889｜kitWaitCountdown 参数名不匹配，还会多按一次返回
- **问题**：

### N-M7｜DesktopMcpServer.kt:40, 54, 74, 98；Main.kt:166-172｜服务端健壮性与并发问题
- **问题与触发场景**：
  - :54 `readText()` 不限大小。网页或本机进程 POST 一个 2 GB 的请求体，就会在 `-Xmx2048m` 下 OOM，桌面端崩溃，未保存的编辑全部丢失。
  - :74 和 :98：`"method": {}` 或 `"name": []` 会让 `.jsonPrimitive` 抛 IllegalArgumentException，handler 异常退出，客户端拿不到 JSON-RPC 错误，只看到连接被断开。
  - :40 `newCachedThreadPool` 线程数不受限，配合大请求体可以耗尽资源。
  - 读与写之间有竞态：`getProject()` 在 HTTP 线程读当前工程，`setProject` 通过 `scope.launch` 异步提交。这两步之间用户在 UI 上的编辑会被整体覆盖（setProjectDirect 是整树替换）。而且响应已经写着「已应用」，实际还没生效；同时用户当前的模块作用域和选中状态也会被重置（ProjectRepo.kt:552-553）。
- **修复**：用 `exchange.requestBody.readNBytes(MAX + 1)` 限制在 1 MB 左右，超出返回 413。整个 handler 包一层 `try { … } catch (e: Exception) { rpcError(-32603) }`，并且保证 `exchange.close()`。改用固定大小线程池，比如 `newFixedThreadPool(2)`。setProject 改成在 Main 线程上用 `withContext(Dispatchers.Main)` 同步执行「重新读取工程 → guard → 写入」，写入时比对版本号。

### N-M8｜BlockPatch.kt:62-75, 89-90, 127, 168-196；StudioState.kt:824-852｜补丁找不到目标时静默跳过，却报成功
- **问题**：parentId 或 blockId 不存在时，insert、update、remove 都静默什么也不做。树遍历只覆盖 `root`，不看 `modules`。guard 也只看 `root.children["body"]`。

### N-M9｜FlowIrImporter.kt:43-53, 147-153, 169-174；StudioState.kt:870-886｜IR 导入丢失安全策略，畸形输入会抛异常
- **问题**：
  1. 只取了 `policy.maxRuntimeMs`。Jingdou IR 的 `policy.skipKeywords / riskyActivityRe / forbiddenZones / riskKeywords` 全部丢弃，导入后护栏比原 IR 更弱，叠加 N-S1 之后等于没有护栏。

  4. `mapNode` 递归不限深度，深层嵌套的 `steps` 会导致 StackOverflowError。
- **修复**：给 kitBoot 增加 policy 参数（或者一个 JSON 参数），把原样的 policy 透传过去。未映射的节点保存成 comment 加入 notes 统计。所有字段改用 `(x as? JsonPrimitive)?.contentOrNull`。递归深度限制在 32 以内。importScript 加上与 importProject 同样的 try/catch。

### N-M10｜desktop/build.gradle.kts:30-53；Main.kt:164-179｜打包版很可能没有 jdk.httpserver 模块（待确认）
- **问题**：DesktopMcpServer 用的是 `com.sun.net.httpserver`，属于 `jdk.httpserver` 模块。Compose 的 nativeDistributions 用 jlink 生成精简运行时，默认模块列表里没有它，而这里也没有写 `modules("jdk.httpserver")`。`runCatching` 会把 NoClassDefFoundError 一起吞掉，MSI 版里 MCP 功能会悄无声息地消失。
- **修复**：先跑 `./gradlew suggestRuntimeModules` 核实，然后在 `nativeDistributions { modules("jdk.httpserver") }` 里加上。启动失败时在 UI 上显示原因。

### N-M11｜Aj6KitRuntime.kt:59-66, 108｜真机上用户按停止可能被 Kit 吞掉（待确认）
- **问题**：`call()` 用 `try { r[name].apply(...) } catch (e) { }`，失败后再 `eval(name)` 并再次 catch。AutoJs6 的停止机制是在 sleep 中抛出中断异常（ScriptInterruptedException）。如果它被包装成 JS 能捕获的异常，sleep 会立刻返回，`guardRisk`（90s）、`waitCountdown`（120s）、`launch`（2×20s）这些循环就会按真实时间空转，用户按了停止，脚本仍在跑，还可能继续点击。模拟器里不受影响：SimAbort 继承 Error，JS 捕获不到（SimRuntime.kt:20）。
- **修复**：catch 里识别中断后重新抛出，例如 `if (String(e).indexOf('Interrupted') >= 0 || (typeof threads !== 'undefined' && threads.currentThread().isInterrupted())) throw e;`。最好只对查询类 API 做吞异常，sleep、click 这类动作直接调用，不要包 try。

## 五、总体评价

新代码的方向是对的：外部调用先脱敏、URL 先校验、AI 改动走补丁护栏、Kit 运行时全部用 ES5 写且所有设备 API 走 PRIM 封装层，结构清楚。Kit 是纯 JS，**没有削弱 SimRuntime 的沙箱**：没有新增 Java 互操作、反射、文件或网络访问，也不另起线程。所有等待循环都经过 `PRIM.sleepIn` 走模拟器的 `sleep`，会执行 `checkLimits()`，时间用的是 `__simNow` 虚拟时钟，所以遵守停止和超时。

主要问题在**集成层**：
1. 积木生成的代码和运行时的 API 对不上：policy、倒计时参数、id 定位、返回值都没接好。结果是对用户宣称的风控、危险页、禁点带、超时护栏实际上全部不生效（N-S1、N-M3、M4、M5、M6）。
2. 新开放的两条外部入口（本地 MCP 服务、LLM 回填）配的补丁护栏只是一个黑名单正则，再加上 MCP 服务没有鉴权，形成了「网页 → 本地 MCP → 注入代码 → 用户点真机运行」的完整攻击链（N-S2、N-S3）。
3. 脱敏只按键名判断，对真实的抓包格式基本无效（N-S4）。
4. SSRF 校验只在字符串层面做，可以绕过（N-M1）。

测试大多停留在冒烟程度，关键风险点几乎都没有负向用例。

## 七、优先修复前 5 项

1. **N-S1**：kitBoot 改为生成 `policy:{…}`，并补一条在模拟器里验证危险页回退的测试。这是对用户宣称的安全能力，修复成本最低、收益最大。
2. **N-S2 + N-M7**：本地 MCP 服务加随机令牌，校验 Host 和 Origin，要求 JSON Content-Type，限制请求体大小，默认关闭。
3. **N-S3**：BlockPatch 改为递归白名单校验，禁止 rawJs 和 CODE/EXPR 参数，标识符参数强制校验；外部补丁之后、真机运行之前要求用户确认。
4. **N-S4**：脱敏补上 HAR 的 name/value 结构、Cookie 和头部行模式、字符串形式 JSON 的递归解析，补上 `wskey` 等键名；发往云端前让用户预览确认。
5. **N-M3/M4/M5 + N-M2**：kit 积木检查返回值，guard 失败就停，未完成的计入 leftover；修正 waitCountdown 的参数名，去掉多余的 back；在 LlmClient 和 StudioState 里恢复「先重抛 CancellationException」。

（紧随其后：N-M1 SSRF 改为按解析后的地址校验，N-M10 打包加上 jdk.httpserver。）
