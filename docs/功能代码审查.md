# AutoJs6 Studio 功能实现代码审查报告

> 范围：`shared/src`（commonMain / jvmAndroidMain / jvmMain / androidMain）、`desktop` 与 `androidApp` 入口，抽查 `jvmTest`。不含 UI 样式。
> 方式：只读审查。没有修改任何文件，也没有运行代码。行号对应审查时的源码。
> 标注"待确认"的条目：代码依据明确，但结论还取决于运行时、第三方库或设备行为，需要用 PoC 或真机验证。

## 一、严重

### S1. Rhino 沙箱只靠黑名单 ClassShutter，可以绕过（桌面与 Android 都受影响）
- **位置**：`jvmAndroidMain/.../runtime/SimRuntime.kt:61`（`setClassShutter { !isJavaClass(it) }`）、`:679-683`（`isJavaClass` 黑名单）、`:151`（`context.initStandardObjects()`）
- **问题**：
  - 黑名单只拦 `java.` `javax.` `jdk.` `sun.` `com.sun.` `org.mozilla.javascript` `kotlin.`。
  - `initStandardObjects()` 会注册 LiveConnect（`Packages`、`JavaAdapter`、`getClass`）。所以类路径上其他包仍然能通过 `Packages.xxx` 访问。
- **场景**：
  - **桌面**：Ktor 3 自带 `kotlinx.io`，类似 `Packages.kotlinx.io.files.FileSystemJvmKt.getSystemFileSystem()` 的写法可以拿到文件系统对象。调用参数是 JS 字符串，不会经过 ClassShutter；返回对象的类名也不在黑名单里。这样就能读写任意文件。另外 `io.ktor.*`、`okio.*`、`cn.dumate.a6studio.*`、`androidx.compose.*`、`org.jetbrains.skia.*` 都可以访问。
  - **Android**：`android.*`、`dalvik.*` 完全没拦。`Packages.android.app.ActivityThread.currentApplication()` 能拿到 Application Context，`dalvik.system.DexClassLoader` 能加载任意代码，读取 `filesDir` 里的令牌也只需一步。
  - 导入的 `.js` 脚本和 `rawJs` 积木都会在模拟器里执行，所以这是"打开别人的脚本就中招"的入口。
- **测试缺口**：`SimSandboxTest` 只测了 `java.*` 三种写法，没覆盖其他包。
- **修复建议**：改成白名单，并且不注册 LiveConnect。
  ```kotlin
  // makeContext()
  setClassShutter { false }                         // 一律拒绝；模拟器不需要任何 Java 类
  // newScope()
  val sc = context.initSafeStandardObjects(null, false)   // 不注册 Packages/java/JavaAdapter/getClass
  ```
  然后补测试：`Packages.kotlinx`、`Packages.io.ktor`、`Packages.cn.dumate`、`Packages.android`、`getClass`、`JavaAdapter` 都必须报错。

### S2. Android 默认禁止明文 HTTP，真机桥接很可能连不上（高置信，请真机确认）
- **位置**：`androidApp/src/main/AndroidManifest.xml`（没有 `usesCleartextTraffic`，也没有 `networkSecurityConfig`）、`androidApp/build.gradle.kts:16`（`targetSdk = 35`）、`config/AppConfig.kt:17`（默认地址 `http://192.168.1.100:9637/mcp`）
- **问题**：targetSdk ≥ 28 时，系统默认不允许明文流量。OkHttp 引擎会抛 `UnknownServiceException: CLEARTEXT communication ... not permitted`，`McpClient.post` 再把它归类成 `NETWORK`（`McpClient.kt:143-145`）。
- **场景**：Android 版对局域网 MCP 的所有操作（连接、拾取、体检、录制、真机运行）都会失败。用户看到的提示是"检查 Wi-Fi/IP"，方向是错的。
- **修复建议**：加 `res/xml/network_security_config.xml`，只对局域网放开明文（或者设 `android:usesCleartextTraffic="true"`，并说明理由）：
  ```xml
  <network-security-config>
    <base-config cleartextTrafficPermitted="true" /> <!-- 或只针对用户配置的 IP 段 -->
  </network-security-config>
  ```
  另外建议在 `networkMessage` 里识别 `CLEARTEXT` 关键字，给出准确提示。

### S3. 读取失败被当成"没有项目"，下一次编辑就会覆盖用户文件（数据丢失）
- **位置**：`store/ProjectRepo.kt:68-71`、`jvmMain/.../DesktopProjectStorage.kt:13-14`、`androidMain/.../AndroidProjectStorage.kt:9-10`
- **问题**：
  - 两个 Storage 都用 `runCatching { file.readText() }.getOrNull()`，读取异常（文件被其他进程独占锁定、权限、I/O 错误）直接变成 `null`。
  - `ProjectRepo.load()` 又 `catch (e: Exception) { null }`，然后走 `raw.isNullOrBlank()` 分支：载入示例项目，并 `return null`。这条路径既不备份，也不提示。
  - 第 84-86 行的 `root.type.isEmpty()` 分支也一样，静默换成示例项目。
- **场景**：Windows 上杀毒软件或同步盘短暂锁住 `project.json` 时启动应用，就会载入示例项目。用户一改积木就 `save()`，原文件被永久覆盖。代码里已经为"解析失败"做了备份，但"读取失败"这条更隐蔽的路径没处理。
- **修复建议**：区分"文件不存在"和"读不出来"。读取失败时抛出或返回错误，并进入只读保护状态（不自动保存，直到用户确认）。
  ```kotlin
  override fun loadRaw(): String? = if (!file.exists()) null else file.readText() // 让异常上抛
  // ProjectRepo.load()
  val raw = try { storage.loadRaw() } catch (e: Exception) {
      readOnlyGuard = true                   // save() 检查此标志
      return "项目文件读取失败（${e.message}），已暂停自动保存以免覆盖"
  }
  ```

### S4. 项目文件不是原子写入，而且每次按键都写盘
- **位置**：`DesktopProjectStorage.kt:16-19`、`AndroidProjectStorage.kt:14-16`（`file.writeText(json)`）、`ProjectRepo.kt:107-114`、`StudioState.kt:298-303`；`ui/canvas/CanvasPanel.kt:346/355/362` 的 `onValueChange` 每个字符都调 `updateParam`（内部 `save()`）再调 `commit()`（又一次 `save()`）
- **问题**：`writeText` 会先截断再写。进程崩溃、断电、Android 被杀都可能在中途发生，留下半截 JSON。下次启动解析失败，备份的也是这份残缺内容，等于丢失。而每次按键写两次盘，大大增加了命中这个窗口的概率，还在主线程做同步 I/O。
- **修复建议**：
  ```kotlin
  override fun saveRaw(json: String) {
      file.parentFile?.mkdirs()
      val tmp = File(file.parentFile, file.name + ".tmp")
      tmp.writeText(json)
      // 可选：保留上一版
      if (file.exists()) file.copyTo(File(file.parentFile, file.name + ".bak"), overwrite = true)
      java.nio.file.Files.move(tmp.toPath(), file.toPath(),
          StandardCopyOption.REPLACE_EXISTING, StandardCopyOption.ATOMIC_MOVE)
  }
  ```
  Android 可以直接用 `androidx.core.util.AtomicFile`。保存改为防抖（例如 300ms）后在 `Dispatchers.IO` 上串行执行，并去掉 `updateParam` 与 `commit` 的重复保存。加载时，主文件解析失败就尝试 `.bak`。

### S5. 脚本导入把字符串拼接、转义和模板字符串当成纯文本，导入后脚本行为改变
- **位置**：`importer/ScriptImporter.kt:42-56`（toast/log/launchPackage/openUrl/kill）、`:63-83`（text/desc/id…click），正则都是 `(['"`])(.*?)\1\s*\)`
- **问题**：`(.*?)\1` 在回溯后能匹配到"最后一个同类引号"，拿到的内容是**源代码片段**，不是字符串值。
  - `toast("已完成 " + n + " 个")` 匹配成功，text 变成 `已完成 " + n + " 个`，生成 `toast("已完成 \" + n + \" 个")`。原来的表达式变成了字面量。
  - `toast('it\'s')`：存进去的是含反斜杠的原文 `it\'s`，`Js.quote` 再转义一次，最终显示 `it\'s`。
  - `` toast(`hi ${name}`) ``：插值丢失。
- **场景**：类注释承诺"生成的脚本与输入等价"，但带变量的提示和日志很常见，导入后会静默改变行为，用户很难察觉。
- **修复建议**：只在参数是**单个、完整且不含转义的字面量**时才映射，否则保留为 raw：
  ```kotlin
  private val strLit = Regex("""^\s*(['"])((?:(?!\1)[^\\\n])*)\1\s*$""") // 不含转义、不含同类引号
  // 反引号一律不映射；含 "\\" 的字面量要么按 JS 规则反转义，要么保留 raw
  ```
  补测试：`toast("a" + b + "c")`、`toast('it\'s')`、`` toast(`x${y}`) `` 导入后都必须保持 rawJs，或者生成代码与原文等价。

## 二、中等

### M1. `CancellationException` 被到处吞掉，结构化取消失效
- **位置**：
  - `McpClient.kt:143-145`（`catch (e: Exception)` 转成 `NETWORK`）、`:174-176`（转成 `TIMEOUT`）、`:290-296`（`runCatching`）
  - `PickerController.kt:109, 131, 145, 171, 211`
  - `AuditController.kt:121, 143, 154`
  - `RecorderController.kt:192, 205, 213, 232`
  - `StudioState.kt:499, 513, 526, 913`
- **问题**：用户关闭面板时 Job 被取消，但取消异常被包成 `BridgeException("连不上…")`，或者被当成普通错误写进状态。
- **场景**：
  - `PickerController.selectNode` 的候选循环（131 行）在取消后会把每个候选都标成 error，并继续 `update(...)`。
  - `refresh()` 在 `close()` 之后仍会写入 `error="...was cancelled"`。
  - 用户还会在日志里看到"连接失败：StandaloneCoroutine was cancelled"之类的误导信息。
- **修复建议**：所有 `catch (e: Exception)` 之前先重新抛出取消异常；`runCatching` 改成不吞取消的版本：
  ```kotlin
  } catch (e: CancellationException) { throw e
  } catch (e: HttpRequestTimeoutException) { ... }
  inline fun <T> runCatchingNonCancel(block: () -> T) = runCatching(block).onFailure { if (it is CancellationException) throw it }
  ```

### M2. 协程里未捕获的非 `BridgeException` 会让应用崩溃（Android 尤其明显）
- **位置**：`StudioState.kt:71`（scope 没有 `CoroutineExceptionHandler`）、`:377-400`（`run()` 只有 try/finally）、`:464-475`（`runTests` 同上）、`:442`（`runOnDevice` 只 catch `BridgeException`）
- **可能抛出的非 Bridge 异常**：
  - `McpClient.kt:311/470` `rpc(...).jsonObject`：`result` 缺失时返回 `JsonPrimitive("")`，`.jsonObject` 抛 `IllegalArgumentException`
  - `:260` 响应是数组时同样抛 `IllegalArgumentException`
  - `:424` `uiDumpJson` 直接 `parseToJsonElement`，失败抛 `SerializationException`
  - 模拟器里的 `OutOfMemoryError` / `StackOverflowError`：`SimRuntime.execute` 只 catch `Exception`（`:110`）
- **场景**：设备插件返回的格式有一点不符合预期，Android 进程就直接崩溃（Main dispatcher 上未处理的异常会交给线程的 uncaught handler）。
- **修复建议**：
  ```kotlin
  val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main + CoroutineExceptionHandler { _, t ->
      toast("内部错误：${t.message}"); runStatus = "异常"; runStatusLevel = "err"
  })
  ```
  在 `McpClient` 内部把解析异常统一包成 `BridgeException("BAD_RESPONSE")`。`run`/`runTests` 用 `catch (t: Throwable)` 生成一个 error 状态的 `RunResult`。

### M3. 模拟器的停止和超时只对解释执行的 JS 指令有效，原生阻塞和内存炸弹无法中断
- **位置**：`SimRuntime.kt:49-65`（只有 instructionObserver）、`:282-288`（`textMatches` 等直接用用户输入构造 Kotlin `Regex`）、`StudioState.kt:379`（在共享的 `Dispatchers.Default` 上阻塞运行）
- **场景**：
  - `textMatches("(a+)+$")` 对长文本、JS 里 `/(a+)+$/.test(...)`、`"x".repeat(1e9)`、`while(1) arr.push(new Array(1e6))`。正则回溯或原生循环期间不会触发 `observeInstructionCount`，停止按钮无效。`running` 一直是 true，`run()` 在 343 行直接 return，用户只能重启应用。内存炸弹会让整个桌面或 Android 应用 OOM。
  - 解释器模式下 JS 递归用的是堆上的帧，没有 `maximumInterpreterStackDepth` 限制，也会把堆耗尽。
- **修复建议**：
  - `makeContext` 里设置 `maximumInterpreterStackDepth = 2000`。
  - 用专用线程（`Executors.newSingleThreadExecutor` + daemon）运行模拟。超时后先 `control.cancel()`，过宽限期仍未返回就把 UI 状态置为超时，并放弃这个线程，至少保证 UI 可恢复。
  - 给传入 Kotlin `Regex` 的输入包一层 `CharSequence`，在 `charAt` 里调 `checkLimits()`（常用的"可中断正则"做法）。
  - 给 `files`/`storage`/日志的总量设上限。

### M4. 积木生成固定的 `let` 变量名，同一作用域放两次同类积木会导致整段脚本语法错误
- **位置**：`catalog/Catalog.kt:458`（`dumpUi` 的 `let _nodes`）、`:482/490`（`jdSign` 的 `signNode`/`moreMark`）、`:497`（`jdOpenPanel` 的 `entry`）、`:517`（`jdTaskLoop` 的 `_roundTasks`）、`:577`（`jdFinishGuard` 的 `emptyRounds`）；用户命名的同名变量也会冲突，如 `:116/226/244/251/308/372/401/419/449` 的 `let $name`
- **问题**：Rhino 在 ES6 模式下，同一块作用域里重复的 `let` 是**编译期**错误（redeclaration）。只要出现一次，整段脚本都不执行。`GeneratedSyntaxTest` 只逐块解析，测不出组合场景。
- **场景**：初学者把"输出控件摘要"拖两次，或者在两处写"记录当前包名到 pkg"，运行时直接报错，而且报错和自己做的操作对不上。
- **修复建议**：模板内部的变量统一改用 `c.newVar(...)`，或者把整段模板包进 `{ ... }` 块。对用户命名的变量，在 `Diagnose.scan` 里加"同一作用域重复声明"的检查，必要时把第二次声明降级为赋值。补一个"每种积木放两次也能解析"的组合测试。

### M5. 多处文本没有转义就拼进注释或代码，可能破坏语法或被注入
- **位置**：
  - `CodeGen.kt:61`（项目名直接放进 `/** */`）
  - `:51`（模块 desc 放进 `/** */`）
  - `:52`（`m.args` 直接拼进函数签名）
  - `:44`（`e.message` 放进 `//` 注释）
  - `:36`（`//@${b.id}`）
  - `Catalog.kt:93`（注释积木只替换 `\n`）
  - `:161` + `:636`（`escForString` 不转义换行和 U+2028/2029）
- **场景**：
  - Windows 上粘贴 `"说明\r\n下一行"` 到注释积木，结果是 `// 说明\r 下一行`。`\r` 在 JS 里是行终止符，"下一行"会被当成代码执行或报语法错误。
  - 项目名或模块说明里含 `*/`，注释被提前闭合，后面的文字变成代码。导入的 `.a6proj.json` 可以借此注入代码，而 UI 上看不出来。
  - `whileGuard` 的条件写成多行时，`log("循环保护触发: a\nb")` 是未闭合的字符串。
- **修复建议**：
  ```kotlin
  fun commentSafe(s: String) = s.replace(Regex("[\r\n\u2028\u2029]"), " ").replace("*/", "*\\/")
  // whileGuard:
  "{ log(${Js.quote("循环保护触发: $cond")}); break; }"
  ```
  `m.args` 和 block id 要校验格式（标识符列表 / `[A-Za-z0-9_]+`），不合法就拒绝或清洗。

### M6. 录制轮询与"录制期间不通信"的设计矛盾，录制状态会被打乱；旧录制会重复生成积木
- **位置**：`StudioState.kt:856-860, 904-919`；`RecorderController.kt:65-67`（注释说明录制期间 MCP 不应答）、`:218`（`fetchEvents` 一进来就把状态改成 FETCHING）、`:82-87`（设备脚本只 append，不清空文件）、`:185`（`start()` 把 `inserted` 重置为 0）
- **问题**：
  - `startTick` 在录制期间每 900ms 调一次 `fetchEvents()`，这与设计说明直接冲突。
  - 第一次调用就把状态改成 FETCHING，接着变成 DONE 或 ERROR（录制期间 MCP 会超时 12s，所以多半是 ERROR，`deviceStatusLevel` 也被标成 err），循环条件不再满足，轮询退出。UI 显示"读取失败"，而手机其实还在录。
  - `fetchEvents` 自己吞掉了所有异常，所以 `fails` 计数永远不会增加。
  - 设备脚本只追加不截断。第二次录制读回来的是"旧事件 + 新事件"，而 `inserted` 已归零，旧操作会再生成一遍积木。
- **修复建议**：录制期间不要轮询（或者轮询时不改 `status`、只更新计数）。设备脚本开始时先清空文件，或者每次用带会话 id 的文件名：
  ```js
  try { files.write(OUT, ""); } catch (e) {}
  ```

### M7. 参数编辑不能撤销，撤销反而会回滚所有参数修改；数字框输不了小数
- **位置**：`ProjectRepo.kt:334-341`（`updateParam` 默认 `snapshot=false`）、`CanvasPanel.kt:346`（`ParamValue.Num(it.toDoubleOrNull() ?: 0.0)`）、`Model.kt:34`（`asText` 把 `1.0` 显示为 `1`）
- **场景**：
  - 添加一个积木后（产生快照）连续改了 10 分钟参数，再按一次撤销，会退回到添加之前，10 分钟的输入全部丢失。
  - 数字框里输 `0.`，被解析成 0.0，再显示成 `0`，小数点立刻消失，`findImage` 的阈值 0.85 根本输不进去；输 `-` 会变成 0。
  - 输入 `NaN` / `Infinity` 时，`toDoubleOrNull` 照样接受，而 kotlinx JSON 默认不允许特殊浮点值，之后每次 `save()` 和 `snapshot()` 都失败（快照被静默跳过）。导入 `sleep(1/0)` 也会走到这条路径（`ScriptImporter.kt:313`）。
- **修复建议**：
  - 文本类参数在获得焦点时、或按 500ms 合并的方式打一次快照。
  - 数字框在本地保留原始字符串，失焦或能完整解析时再写回，并拒绝非有限值：
    ```kotlin
    it.toDoubleOrNull()?.takeIf { d -> d.isFinite() }?.let { d -> repo.updateParam(..., ParamValue.Num(d)) }
    ```

### M8. Android 重建 Activity 时会丢回调、导出空文件，导出失败也报告成功
- **位置**：`MainActivity.kt:38-39, 68`（`pendingOpen`/`pendingSave`/`pendingSaveData` 是 Activity 字段）、`:59-65`（写入失败被 `runCatching` 吞掉，但仍回调文件名）、`:103-118`（`suspendCancellableCoroutine` 没有 `invokeOnCancellation`）、`:162-174`（StudioState 放在 `remember` 里）
- **场景**：
  - Manifest 只声明了 orientation/screenSize 等配置变更。深色模式切换、语言或字体缩放变化、以及在 SAF 选择器停留时进程被回收，都会重建 Activity：
    - 新实例的 `pendingSaveData == null`，`CreateDocument` 已经创建了一个**空文件**，内容丢失；
    - 旧协程永远不会 resume；
    - `StudioState` 重建：正在运行的模拟被取消，undo 栈、录制的 `executionId`（无法再停止手机脚本）、没勾"记住"的令牌全部丢失。
  - 写入失败（存储已满、Provider 异常）时也会显示"已导出"。
  - `openOutputStream(uri)` 默认模式 "w" 在部分 DocumentsProvider 上不会截断旧内容（待确认）。
- **修复建议**：把 `StudioState` 放进 `ViewModel`（`onCleared` 里 dispose），待写入的数据放进 ViewModel 或 `SavedStateHandle`。`openOutputStream(uri, "wt")`，写入失败时回调 `null`。`invokeOnCancellation { pendingOpen = null }`。

### M9. 令牌明文存储，Android 还会进入系统备份；桌面权限是写完后才设置
- **位置**：`StudioState.kt:591-598`、`MainActivity.kt:96-101`、`AndroidManifest.xml`（没有设置 `allowBackup`，默认为 true）、`desktop/Main.kt:60-75`
- **问题**：
  - Android：`filesDir/a6studio.tokens.v1` 是明文，而且默认参与 Auto Backup（云端）和 adb backup。拿到备份就拿到了能控制手机（`shell_exec`、`script_run`）的令牌。
  - 桌面：文件先按默认 umask 创建（通常是 644），再改成 600，中间存在一个 TOCTOU 窗口。Windows 上没有任何 ACL 加固。
  - `Main.kt:50` 的 `resolve()` 遇到绝对路径直接放行，与注释里"限制在配置目录内"的说法不一致。
- **修复建议**：
  - Android 用 Keystore 加密（EncryptedSharedPreferences / Tink），manifest 里设 `android:allowBackup="false"` 或配置 `dataExtractionRules` 排除令牌文件。
  - 桌面用 `Files.newByteChannel(path, setOf(CREATE_NEW, WRITE), PosixFilePermissions.asFileAttribute(...))` 在创建时就带上权限，再原子替换；Windows 可以考虑 DPAPI。
  - `resolve()` 拒绝绝对路径。

### M10. McpClient 的会话和并发处理
- **位置**：`McpClient.kt:302-304`、`:72-77`、`StudioState.kt:479-482`、`McpClient.kt:250-265`、`:209-231`、`:147-149`
- **问题**：
  1. `ensureReady()`（302-304）没有在锁内二次检查。两个协程（例如体检和拾取同时进行）都看到 `!ready`，就会串行执行两次 `initialize`，后一次覆盖 `sessionId`，前一个会话的后续请求可能被设备拒绝。
  2. `applyBridgeConfig()` 每次都调用 `setUrl()`（`StudioState.kt:479-482` → `McpClient.kt:72-77`），即使地址没变也会把 `ready` 置为 false、清空 `sessionId`。真机运行（70s）还在进行时打开拾取器，会话就被重置并重新握手。
  3. `rpc()`（250-265）不校验响应的 `id`。SSE 只取"第一个完整的 JSON"（209-231），如果服务端先推送 `notifications/progress` 或服务端请求，会被当成结果，表现为 `result` 缺失，进而触发 M2 的崩溃（待确认：取决于插件是否推送此类消息）。
  4. 会话过期时，MCP 规范要求返回 404，这里被归类为 `BAD_ENDPOINT`（147 行），提示"地址不是 MCP 端点"，方向错误，也没有自动重新握手。
- **修复建议**：
  ```kotlin
  private suspend fun ensureReady() { if (!ready) mutex.withLock { if (!ready) initializeLocked() } }
  fun setUrl(newUrl: String) { val u = normalizeUrl(newUrl); if (u == url) return; ... }
  ```
  - SSE 跳过没有 `id`、或 `id` 与请求不一致的消息，继续往下读。
  - 带着 `sessionId` 收到 404 时，清空会话、重新 `initialize`，并重试一次。

### M11. Ktor 3 的 `http.post{}` 默认会把整个响应体读进内存，SSE 的逐事件读取可能没有生效（待确认）
- **位置**：`McpClient.kt:130-140, 214`
- **问题**：Ktor 3.0.x 的 `HttpClient.post {}` 走 `HttpStatement.execute()` 加 SaveBody：响应体会先完整读入内存，再返回 `HttpResponse`。如果设备真的保持 SSE 长连接不关闭，`http.post` 本身就会一直阻塞到 socket 或请求超时，后面的 `readFirstSsePayload` 读的只是内存里的副本。这和注释"读到第一个事件就返回"的意图不符。目前能工作，可能只是因为插件回完就关闭了连接。
- **修复建议**：改成真正的流式调用：
  ```kotlin
  http.preparePost(target) { ... }.execute { resp -> /* 在这里 bodyAsChannel 逐块读，读到即 return */ }
  ```
  并补一个"服务端保持连接不关闭"的本地 MockEngine/嵌入式服务器测试。

### M12. 体检的 `busy` 标志和 Job 取消存在竞态，重新体检可能什么都不做（待确认）
- **位置**：`AuditController.kt:50, 88-104`；`StudioState.kt:811-814`
- **问题**：`startAudit()` 先 `cancel()` 旧 Job 再 `launch` 新 Job。旧 Job 要等被重新调度、执行完 finally 才会把 `busy` 置回 false。如果新 Job 先被调度，`if (busy) return` 就直接返回，界面停留在被取消的那次结果上。
- **修复建议**：去掉 `busy`，只靠 Job 管理；或者 `auditJob?.cancelAndJoin()` 之后再启动。

### M13. 生成代码中 `files.ensureDir` 的参数用错，可能导致目录没创建（待确认，依据 AutoJs6 文档语义）
- **位置**：`Catalog.kt:381, 393`（传入 `dirname(p)`）、`:630-633`（`dirname`）
- **问题**：AutoJs6 的 `files.ensureDir(path)` 语义是"确保 path **所在**的文件夹存在"（创建的是 path 的父目录）。`RecorderController.kt:82` 自己的设备脚本也是按这个语义直接传文件路径的。这里传的是 `dirname(p)`：对 `/sdcard/autojs6/shot.png` 只会保证 `/sdcard` 存在，`autojs6` 目录不会被创建，`images.save` 和 `files.append` 会失败。另外，`dirname("/x.png")` 返回的是 `"/x.png"` 本身（`idx > 0` 的判断错了），没有斜杠的路径也原样返回。
- **修复建议**：直接 `files.ensureDir(${c.quote(p)})`；`dirname` 在 `idx == 0` 时返回 `"/"`，`idx < 0` 时返回 `""` 并跳过。

### M14. 导入时按分号拆分后丢掉了分号，会触发 ASI 陷阱
- **位置**：`ScriptImporter.kt:286-300`（拆分时丢弃 `;`）、`:231`（raw 片段之间用 `\n` 拼接）
- **场景**：`a = b; (function(){ ... })();` 拆成 `a = b` 和 `(function(){...})()`，以 raw 形式拼回去变成 `a = b\n(function(){...})()`，JS 会把它解析成 `a = b(function(){...})()`。`x = 1; [1,2].forEach(f)` 也一样，语义被改变。
- **修复建议**：raw 片段保留原来的分号（`parts += cur.append(';').toString()`），只有被映射成积木的语句才去掉分号。

### M15. 跨作用域操作与撤销后的作用域不一致
- **位置**：`ProjectRepo.kt:172-192`（`locate` 搜索全部作用域）、`:280-324`（move/shift/duplicate 只操作当前作用域）、`:135-141`（`undo` 不校验 `_scopeState`）
- **场景**：
  - `locate` 在模块里找到了块，`moveBlock` 却在当前作用域执行 remove（找不到，什么也没删）和 insert。结果是同一 ID 出现两份，之后 `TreeOps.replace` 和 `remove` 会同时作用在两份上。
  - 撤销"新建模块"后，`_scopeState` 仍指向已不存在的模块。之后 `withBody` 什么都不更新，但仍然快照、保存、提示"已添加"，用户添加的积木悄无声息地消失。
  - 加载或导入项目时 `normalizeBlock`（97-99）不修复空 ID 或重复 ID（`TreeOps.normalize` 没有被调用）。
- **修复建议**：`locate` 只在当前作用域查找，或者让 move/duplicate 根据 `loc.parentId` 选择目标作用域。`undo()` 之后如果 `currentModule() == null` 就 `setScope(Scope.Root)`。加载和导入时遍历一遍，重新分配重复或空的 ID。

## 五、总体评价

代码整体质量不错：注释里记录了大量真机实测结论，像字符串统一转义、Context 泄漏、按 URL 归一化令牌、解析失败先备份这类"踩过的坑"都有针对性的修复和回归测试，模块边界（RunEngine 接口、纯逻辑的 PickerLogic、可单测的 SseFrames）也清晰。

主要风险集中在四处：
1. **安全边界**：模拟器沙箱用的是黑名单，导入的脚本可以逃逸到宿主（桌面和 Android 都受影响）。
2. **数据持久化**：读取异常被吞掉、写入不是原子的、每次按键都写盘，三者叠加有真实的数据丢失路径。
3. **平台适配**：Android 的明文 HTTP 策略很可能让真机功能整体不可用；Activity 重建会丢状态；令牌会进入系统备份。
4. **协程错误处理**：普遍吞掉 `CancellationException`，scope 也没有异常处理器，非 Bridge 异常可能让应用崩溃。

代码生成和导入属于"大体正确、边界未封口"：变量名冲突、注释注入、导入时把表达式当成字面量，都会让初学者遇到难以理解的失败。

## 六、优先修复前 5 项

1. **S1 沙箱改白名单**：`initSafeStandardObjects()` 加 `setClassShutter { false }`，并补逃逸测试。
2. **S2 Android 明文 HTTP**：加 `network_security_config`，并在真机上验证连接。
3. **S3 + S4 持久化**：读取异常时禁止自动覆盖，改为原子写入并保留 `.bak`，保存做防抖并移到 IO 线程。
4. **S5 + M14 导入器**：只映射纯字面量参数，raw 片段保留分号，补等价性测试。
5. **M1 + M2 协程错误处理**：全局重抛 `CancellationException`，给 scope 加 `CoroutineExceptionHandler`，McpClient 把解析异常统一包成 `BridgeException`，`run`/`runTests` 捕获 `Throwable`。

紧随其后的是 M3（停止按钮在原生阻塞时失效）和 M4（重复 `let` 导致整段脚本无法运行），两者对初学者体验影响最大。
